# 継手APIの要件

社内のAPIを一か所で探し、使う目的を伝えて申請し、承認されたら呼び出せるようにする。

[要件ファイルを読む](items/) · [要件テンプレート](template.md) · [画面仕様と業務フロー](../design/portal.md)

## 要件を追加する

1. 新しい要件を提案するときは `feat/<変更名>` ブランチを作り、テンプレートを `items/` にコピーする。既存要件の誤記修正などは変更内容に合うブランチを使う。
2. 「Aは、Bのとき、Cできる」の順に書く。「承認したとき」のような動詞の条件も使える。ファイル名は見出しから太字の記号を外した全文に `.md` を付ける。句点や連番は付けない。
3. 主体・条件・操作に使う共通語彙は見出しで **太字** にする。既存の用語は表記と意味を引き継ぐ。新しい用語は、その用語を最初に説明する要件の本文に一度だけ `**用語**（意味）` と書く。「API」と「商品」、「掲載停止」と「利用権取消」のように、判断の違う概念を区別する。
4. 4つの見出しに短く記入する。「決めた方針」には、その動作を確かめられる条件や結果を書く。「却下した方針」は採用しない選択肢を記す。過去の議事録がない場合は、仕様で明確に除外した動作を書くか「却下の記録なし」とする。

## 要件一覧と用語一覧を読む

main向けPRの **Verify** が原本を検査して一覧を生成する。実行結果の **requirements** 成果物を展開し、`index.md` で主体別の要件、`glossary.md` で用語の意味と定義元を確認する。どちらからも同梱の要件本文へ移動できる。手元でもリポジトリ直下から同じ文書を生成できる。

```sh
python tools/design/requirements.py
```

出力先は `artifacts/requirements/`。要件ファイルが増減すると次回の生成で一覧に反映される。機能追加のPRでは分岐点からの差分に新しい要件ファイルが1件以上必要になる。既存ファイルの編集・改名、テンプレートや一覧の更新は追加に数えない。

## 機能変更と証跡を更新する

1. 最新のmainからの差分で、利用者・提供者・管理者・開発者が新しくできることを洗い出す。新機能ごとに原本を追加し、既存機能の条件変更は該当原本を更新する。参照する画面仕様とREADMEの操作名も照合する。
2. 変更した原本の「受入テスト」に実在するpytest関数を指定する。ブラウザーE2Eでは成功時にそのケースが保存する画像名も指定する。「変更履歴」に `- YYYY-MM-DD 理由` を1行追記する。
3. Verifyは `feat/`・`feature/` ブランチ、PR件名・本文の行またはコミット件名の `feat:`・`feat(範囲):`、PR本文の独立した行 `要件への影響：機能追加` を検出する。機能追加には新規原本が必要。実装（packages配下のsrc・public）だけを変えた場合は、PR本文の独立した行 `要件への影響なし：理由` で、利用者から見た動作が変わらない根拠を示す。
4. コミット後に `python tools/design/requirements.py --branch "$(git branch --show-current)" --base origin/main` と `python -m tools.testing.requirement_evidence --check` で検査する。ローカルでPRの記述も検証するときは環境変数 `PR_TITLE` と `PR_BODY` を渡す。
5. PRではVerifyの成果物で対象要件の成否を確認する。マージ後は当該コミットの「Deploy to AWS」と「Publish requirement evidence」の成功、証跡の `Source-merge` を確認する。[証跡と保存履歴](../../evidence/README.md)
