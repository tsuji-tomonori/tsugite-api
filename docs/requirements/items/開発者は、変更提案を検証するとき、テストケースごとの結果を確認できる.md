# **開発者**は、**変更提案**を検証するとき、**テストケース**ごとの結果を確認できる

## 背景

**変更提案**（ブランチの差分をレビューするプルリクエスト）に対し、どの条件を検証したかを知る必要がある。

## なぜ必要か

仕様のどこが壊れたかを、実装を読まずに特定できるようにするため。

## 決めた方針

**テストケース**（条件と期待結果を持つ検証単位）にE2Eを含めて簡潔な日本語の説明を付け、アーキテクチャテストで検査する。レポートには成否・実行時間・該当する画面を含める。

バックエンドと各サンプル商品の公開仕様にIBMのREST設計規則を適用し、500のJSON本文には `error_code` を必須とする。操作ごとに仕様で宣言した各ステータスの実応答を検査し、未到達のステータスがあれば変更提案を不合格とする。

## 却下した方針

テスト関数名だけで業務上の期待結果を説明する運用は採用しない。
