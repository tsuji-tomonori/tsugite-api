# 継手API ポータルの画面仕様

Amazon DataZoneのデータポータルで使う「提供プロジェクトのインベントリ」「公開カタログ」「プロジェクト単位のサブスクリプション」を、APIの公開と利用に対応づける。利用権は商品・利用プロジェクト・環境単位で付与し、本人向けの申請では申請者も区別する。実行時には利用者と認証情報に許可された操作を照合する。

|利用者の仕事|入口と操作|画面で確かめること|
|---|---|---|
|提供者が出品する|提供するAPI → APIを登録 → 下書きを保存 → 詳細で公開申請|提供一覧で現在の承認担当を、商品詳細で申請時の順番と承認済み・承認待ち・未到達の段階を確認する。最終承認と接続確認を経て公開する|
|利用者が選ぶ|APIカタログ → キーワード・環境で検索 → 詳細|用途・提供元・対応環境・OpenAPIの操作を、申請前に確認できる|
|利用を申請する|商品詳細の「利用申請へ進む」→ 専用画面でプロジェクト・対象・環境・目的を指定 → 自分の申請|一覧でステータスと現在の担当を確認し、「承認経路」で段階別の担当・状態・判断理由を読む。承認待ちの申請は取り下げられる|
|提供者が判断する|届いた申請 → 理由を記入して承認または却下|申請者が理由を読める。却下・取下げ後は再申請できる。古い判断の再送は拒否する|
|利用者が実行する|自分の申請 → APIを開く → 承認環境で実行|応答コード・本文・照合用IDを表示する。別環境、別プロジェクト、却下、権限取消では転送しない|
|掲載と権限を終了する|提供するAPIで掲載を取り下げる。届いた申請から権限を取り消す|掲載終了で新規申請を止め、既存の権限は取消まで有効とする|
|本人が結果を確認する|アクセスログ → 呼び出しの行を選ぶ|開始・応答時刻、結果、処理時間を確認し、リクエストID付きで問い合わせできる|
|リーダー・監査担当・管理者が追跡する|監査履歴 → 呼び出しの行を選ぶ|リーダーは担当範囲、監査担当・管理者は全体を確認できる。公開・申請・承認は「業務操作履歴」で操作やリクエストIDを指定する|

## レイアウトと操作

- 背景と同系色の共通ヘッダーに製品名と利用者の所属を表示する。左ナビゲーションで探す・利用する・提供する・監査する仕事を分ける。現在地をパンくずと太字とグレーの選択背景で示す。
- 画面上部の操作結果は右端の「×」で閉じられる。入力中の値は保持される。
- 公開一覧ではAPI名、用途、提供元、環境を同じ位置にそろえる。検索条件は一覧の直前で折りたためるようにし、総件数と表示範囲を明示する。1ページ12件とし、検索し直したら先頭に戻る。
- 一覧の初期表示では検索条件を閉じ、データが十分にあるときに画面の高さの70%以上に表が見えるようにする。入力時はフォームを本文幅に展開する。行が少ない場合は内容に合わせた高さにする。
- 主要操作は背景と明暗を反転させ、リンクには下線、補助ボタンにはグレーの輪郭、利用可能は緑、承認待ちは黄系、却下・拒否は赤とし、状態名を必ず併記する。入力にラベル、操作にフォーカス枠を付ける。
- 狭い画面ではメニューを開くと横断検索と所属名を確認できる。幅400px以下ではログアウトもここで操作する。列が収まらない表は表の中で横にスクロールできる。長い識別子や応答を折り返す。390px幅でページ全体の横スクロールが生じないことを確認する。
- レビューでは公開済みデータを使い、検索、ページ境界、空の検索結果、判断理由、取消後の応答を確認する。自動検証と撮影した実画面を対応づける。

参考資料：[Amazon DataZoneの公開](https://docs.aws.amazon.com/datazone/latest/userguide/publishing-data.html) ／ [サブスクリプション申請](https://docs.aws.amazon.com/datazone/latest/userguide/subscribe-to-data-assets-managed-by-datazone.html)

## 所属・権限と利用状況

|所属・権限|ポータルでできる操作|利用状況の範囲|
|---|---|---|
|管理者|提供ガイドラインと公開審査の設定、ユーザーの追加・削除、全体または所属先への通知、利用上限の設定|全プロジェクト|
|一般利用者|所属プロジェクトでの商品登録・公開申請・編集、商品の利用条件の設定、カタログ検索・利用申請・承認済みAPIの呼び出し|自身と所属プロジェクトで扱うAPI|
|現在の承認担当者|届いた公開申請または利用申請の判断|承認順の現在の段階で割り当てられた申請|
|監査担当|業務監査とアクセスログの照合、メトリクスの閲覧|全プロジェクト|

掲載停止は新規の申請を止める。名称・説明の編集は既存契約を引き継ぐ。OpenAPI・接続先・ベースパスの変更時は下書きに戻し、承認待ちを終了し、利用権を取り消す。削除時も利用権を終了し、監査記録を保持する。ユーザーを削除すると既発行の個人トークンによる利用も停止する。

アクセスログ・監査履歴・メトリクスの期間は、直近の相対期間または「日時指定（UTC）」から選ぶ。日時指定では開始・終了のカレンダーの下で日付と時刻を編集できる。アクセスログ・監査履歴のダウンロードボタンは、検索条件を開いても操作行の右端に表示する。

グラフはポータルのアクセス記録をUTCで集計する。期間、間隔、API、環境、プロジェクト、HTTPステータスと表示指標を選べる。棒を選ぶと、リーダー・管理者・監査担当はその時間帯の監査履歴、それ以外の利用者は本人のアクセスログを開く。アクセスログと業務監査はリクエストIDで照合し、絞り込んだ記録をJSON Linesで保存できる。

上限はAPI・利用プロジェクト・環境の組み合わせごとに、UTCの固定区間で数える。転送前に1件を確保し、上限に達した時点でプロジェクトへ1回通知する。停止設定では次の呼び出しからHTTP 429を返し、期間が変わると自動で再開する。設定変更時は件数をリセットする。ベルの未読は個人別に管理する。

## 部署・プロジェクトと利用権

管理者は「メタデータ」の「部署」で部署の表示名と親を設定する。部・課・係などの区分と階層数は固定しない。ユーザーは上位部署に直接所属でき、部署・プロジェクトを兼務できる。各所属に役職名とリーダー権限を付ける。プロジェクトには任意で管轄部署を指定する。

「属性一覧」には、部署とプロジェクトに「使用中」のデータパーツバッジが付く。属性の定義はキーと表示名、値の名称を公開する範囲を持つ。それぞれの値は1つの項目に属し、利用者は複数の値に所属できる。部署とプロジェクトの識別子、既存の所属、グループごとの役職とリーダー権限を引き継ぐ。

たとえば雇用区分を追加する場合は、管理者が「メタデータ」→「属性一覧」→「項目を追加」で項目名「雇用区分」とキー `employment-type` を登録する。「雇用区分」を開き、「値を追加」で「社員」や「業務委託」を作成し、それぞれの詳細で利用者を割り当てる。利用者は「自分のプロフィール」で設定値とグループ内の役割を確認できる。任意項目のリーダーはその値と下位の値のメンバーを閲覧できる。

項目設定で値の名称を全利用者に公開すると、提供者がAPI商品の公開条件にその値を選べる。限定公開では、指定したプロジェクト・部署・任意属性のいずれかに一致する利用者が対象となる。任意属性はその値への直接所属で判定する。API呼び出しには利用申請と対応する利用権が必要となる。

管理者は部署・プロジェクト詳細の「移管・削除」から、同じ種類の後継組織に所属や利用設定を引き継げる。削除は所属・子組織・有効な契約などを解消してから行う。

「ユーザー管理」「直接の所属メンバー」とモニタリングの所属メンバー表には、ユーザー名と氏名を別々の列に表示する。氏名が空欄なら「未登録」と表示し、異なる表示名があれば氏名に添える。「直接の所属メンバー」にはメールアドレスと担当ロールも表示する。氏名と表示名は「自分のプロフィール」で変更できる。全体管理者は招待時に設定し、「ユーザー管理」から修正できる。招待時はユーザー名（ログイン用メールアドレス）と氏名を必須とする。既存ユーザーもプロフィールを次に保存するときに氏名を入力する。変更は業務監査に実行者、対象者、変更した項目を記録する。

Cognitoで別に登録した利用者の表示用メールを補う場合、対象環境の `HUB_SETTINGS_PARAMETER`、`DSQL_HOST`、`DSQL_USER` を設定し、`uv run --locked --all-packages python -m packages.tools.operations.sync_member_emails` で件数を確認する。反映する場合は同じコマンドに `--apply` を追加する。メール属性を利用者識別子で確認して保存するため、同じメールアドレスを持つ別アカウントの所属とは混ざらない。

全メンバーが所属プロジェクトで商品を登録し、責任を負うプロジェクトまたは個人を指定する。管理者が設定した公開承認順に従い、最後の審査者の承認で掲載する。利用申請の承認順は商品ごと・環境ごとに提供プロジェクトが設定する。

申請対象はプロジェクト全員か本人を選ぶ。チームに所属していない人も「個人ワークスペース」から本人として申請できる。提供者は詳細画面で公開する部署とプロジェクトを選ぶ。部署には子孫部署を含む。検索・詳細表示・申請・呼び出しで公開条件を確認する。

申請者の部署または役職が提供者の指定条件と一致すると、その申請は自動承認される。その他の申請は提供者、または申請者が所属する部署について提供者が指定したリーダーが承認・却下できる。委任先は自分自身の申請を判断できない。プロジェクト単位の承認は同じプロジェクト全体に適用される。本人単位の承認はプロジェクトの共有キーでは利用できない。

## 認証情報と実行権限

「APIキー」で発行先プロジェクトを選ぶと、そのプロジェクトで選べるAPI・操作・利用者・期限が表示される。「すべてのAPI」でも、実際に呼べるのは対象環境で承認済みのAPIだけ。個人申請の権限は本人限定の認証情報で使う。

|方式|発行時に受け取るもの|次のアクセストークンを取得する方法|
|---|---|---|
|短期Bearer|すぐ使えるアクセストークン|ログインして「アクセストークンを取得・更新」。API Docsでも必要時に取得する。|
|アプリ認証|クライアントIDとシークレット|アプリのサーバーが下記の交換APIに利用者のCognitoアクセストークンを付けて送る。|
|システム認証|クライアントIDとシークレット|システムが交換APIにIDとシークレットを送る。呼び出しごとに新しいトークンを取得できる。|

アプリ・システムからは `POST /api/auth/token` に次のJSONを送る。アプリ認証では `Authorization: Bearer <利用者のCognitoアクセストークン>` を付ける。システム認証ではこのヘッダーを省く。シークレットはサーバーで保管する。

```json
{"client_id": "<クライアントID>", "client_secret": "<クライアントシークレット>"}
```

応答の `access_token` を業務APIのBearerに指定する。`expires_in` は失効までの秒数、`refresh_after` は更新を開始できるまでの秒数。ポータルとアプリはこの時刻以降の最初の取得で新しいトークンを発行する。前のトークンは自身の期限まで使える。システムは取得のたびに新規発行する。システムのクライアント資格には固定の失効日はない。シークレットの更新で以前のシークレットと発行済みトークンが失効し、認証情報を失効させると再発行も止まる。

### 有効期間を絞る

提供者はAPI詳細で、部署・プロジェクトのリーダーは「メタデータ」の対象の詳細で上限を設定する。例えば、提供者45分、部30分、課25分、プロジェクト20分のとき、利用者は1〜20分を選べる。兼務や複数APIに上限がある場合は最短の値を使う。上限の短縮は発行済みトークンにも次の実行から適用する。利用者にひも付くトークンはログイン資格の残り時間も超えない。標準は有効60分、45分経過後から更新。更新開始は発行時に有効期間内で指定する。

### 利用者とアプリの権限を設定する

提供者はAPI詳細で利用者を選び、OpenAPIにあるメソッドとパスをチェックする。全選択を外して保存するとその人の全操作が止まる。「個別設定を解除して継承」すると承認済みの範囲に戻る。アプリ発行時にも対象利用者・対象API・操作を選べる。API Docsの選択肢とサーバーの認可には、利用申請、本人の許可、認証情報に設定した範囲のすべてを適用する。監査ではアプリ実行は利用者、外部システム実行はシステム専用の識別子で記録する。

### 従来のAPIキー

`tsu_` で始まるキーは従来どおり共有キー単体、または本人のCognitoトークンと `X-API-Key` の組み合わせで使える。有効期間は最長60分。既発行キーは移行005を適用した時刻から数える。利用者別に操作を制限したAPIで、従来の共有キー単体による呼び出しは拒否する。長期運用するバッチはシステム認証に移行する。

## ハイブリッド検索

キーワード一致と日英の業務概念・OpenAPIタグ説明による意味の近さを別々に順位付けし、両方の順位を統合する。たとえば「両替」から為替APIを探せる。数値化する対象は閲覧可能なAPIだけで、未公開の商品やタグは件数・順位に影響しない。意味検索の範囲は業務語彙と登録されたタグ説明に依存する。
